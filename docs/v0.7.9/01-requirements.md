# v0.7.9 요구사항

2026-11-06 확정(재리 "진행" 02:11). v0.7.7(조각 읽기) 뒤에도 수집 중 앱이 메모리 부족으로 강제 종료됐다. 실측으로 찾은 원인(무거운 글자 찾기 모델)을 고친다. 저장 칸·평가·수집 개수 규칙·화면은 바꾸지 않는다.

## 사용자 의견과 결정

- 11-06 01:43 새 이미지(v0.7.7)로 수집 → 9건 저장 뒤 강제 종료, 다시 수집 → OCR 시작 16초 만에 강제 종료(앱 메모리 약 7.5GB, Docker 한도 7.67GB)
- 재리 PC 실측(앱과 같은 이미지로 띄운 일회용 컨테이너, 상한 6.5GB, 공고 이미지 15장): 기본 설정 `PP-OCRv5_server_det`는 이미지 넓이 1MP당 약 5GB. 860×1582(1.4MP)도 상한 넘음. v0.7.7 조각(최대 1280×1600, 2MP)보다 작아도 넘으므로 조각만으로는 못 막음. 조각을 여러 개 읽어도 최대치는 그대로(쌓이는 문제 아님)
- 같은 1920×9964 이미지: 가벼운 모델 + 긴 변 960은 975MB·3,020자, 큰 모델 + 긴 변 960은 4,612MB·3,014자
- 내 안: 가벼운 모델 + 긴 변 960. OCR을 앱과 다른 프로세스로 돌리는 안전장치는 구조가 바뀌어 이번에 빼고, 또 꺼지면 넣음 → "진행"

## 기능 요구사항

| ID | 내용 |
| --- | --- |
| F1 | 글자 찾기 모델은 `PP-OCRv5_mobile_det`, 한국어 글자 읽기 모델은 `korean_PP-OCRv5_mobile_rec`를 쓴다 |
| F2 | 글자 찾기 때 이미지 긴 변을 960px 이하로 줄인다(`text_det_limit_type="max"`, `text_det_limit_side_len=960`) |
| F3 | v0.7.7의 넓은 이미지 줄이기·조각 읽기·겹친 줄 한 번만은 그대로 둔다. 수집·받은함·이미지로 다시 평가가 모두 같은 설정을 쓴다 |

## 비기능 요구사항

| ID | 내용 |
| --- | --- |
| N1 | 새 의존성 없음. Docker 빌드가 같은 설정으로 모델을 미리 받는다(`scripts/warm_ocr.py`가 `ocr._model()` 호출, Dockerfile 그대로) |
| N2 | 테스트는 PaddleOCR 없이 가짜 모듈로 설정 값만 확인한다 |

## 하지 않는 것

- OCR을 앱과 다른 프로세스로 분리(구조 변경. 가벼운 모델로도 꺼지면 다음 후보)
- Docker·WSL 메모리 한도 바꾸기
- 수집 개수·중복 규칙 변경
